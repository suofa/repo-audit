# 架构与设计取舍

> 这份文档解释 repo-audit 为什么这样实现。面试时被问「你为什么这么设计」，答案都在这里。

## 数据流

```
CLI (src/cli.ts)
   └─ scanRepository()            ← src/core/scan.ts，唯一的编排入口
        ├─ git 封装              ← src/core/git.ts      （spawn git，不引第三方库）
        ├─ 读取被跟踪文件        ← src/core/files.ts    （只读一次，多个指标共享）
        ├─ metrics/*             ← 纯函数，输入数据、输出指标
        └─ 组装 ScanResult
   ├─ scoreScan()                ← src/core/score.ts    （加权 → 总分 + 等级）
   ├─ renderTerminal()           ← src/report/terminal.ts
   └─ renderHtml()               ← src/report/html.ts   （自包含 HTML）
```

**关键分层**：`metrics/*` 是纯函数，不碰文件系统和 git。所有 I/O 集中在 `git.ts` 与 `files.ts`。
这样测试可以只构造数据、不建仓库，跑得又快又稳。

## 六个取舍

### 1. 零运行时依赖

只用 Node 内置模块 + `git` 命令。理由：

- 安装体积小、没有供应链风险（`npm audit` 永远是 0）；
- 评审者 clone 下来 `npm test` 就能跑，不需要理解别人的框架；
- 强制自己写测试运行器用法（`node:test`）、参数解析（手写）——这些恰好是面试爱问的基础。

代价是参数解析和 ANSI 渲染要自己写，约 200 行。值得。

### 2. 用 `git` 子进程，而不是解析 `.git` 目录

解析 Git 对象格式既复杂又容易踩坑（packfile、多 pack、浅克隆）。
`git log --pretty=format:` 是稳定契约，代价是每次扫描有几十毫秒的进程开销。

用 `\x1f` / `\x1e` 作为字段与记录分隔符，避免提交信息里出现冒号、逗号时解析出错。

### 3. 文件只读一次

`size` 和 `debt` 两个指标都要文件内容。如果各自读一遍，大仓库会慢一倍。
`readTrackedFiles()` 返回统一的 `FileSample[]`，两个指标共享同一份快照——顺带还保证了
「两个数字描述的是同一时刻的仓库」。

### 4. 只统计被 git 跟踪的文件

`git ls-files` 而不是遍历目录：`node_modules`、构建产物、IDE 缓存天然被排除，
也不需要自己维护忽略规则。

### 5. bus factor 用 60% 而不是 50%

50% 会让「两人各 50%」判定为 1，明显不合理。60% 意味着「少数人掌握多数提交」，
更贴近真实风险，同时避免两人项目被误判。

### 6. 跳过合并提交

合并提交不携带独立意图，计入会重复统计分支上的工作；跳过它，作者分布才反映真实贡献。

## 为什么权重是这样

| 维度 | 权重 | 理由 |
| --- | --- | --- |
| 工程规范 | 30% | 有测试、CI、文档，才是「别人敢用」的项目；这是学生项目最缺的 |
| 活跃度 | 25% | 最近 90 天的提交比总量更能说明项目是否还活着 |
| 提交质量 | 20% | 提交信息是协作能力最便宜的证据 |
| 技术债 | 15% | 用密度（处/千行）而非绝对值，避免大项目被冤枉 |
| 代码结构 | 10% | 只看规模与超大文件，不做复杂度分析（那需要 AST，超出本工具定位） |

总分是加权平均后四舍五入到一位小数，任何单一维度的极端值都不会让总分失控。

## 扩展点

- 新增指标：在 `src/core/metrics/` 加纯函数，在 `scan.ts` 组装，在 `score.ts` 给权重，补测试。
- 新增输出格式：实现 `renderXxx(result, score)`，在 `cli.ts` 加一个 flag。
- 想接 AI 摘要：把 `ScanResult` 丢给模型即可，指标层不需要改。
